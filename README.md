# IoTSE — портативный инструмент на ESP32-S3

IoTSE — собственная прошивка для портативного устройства на **ESP32-S3 N16R8**. Цель проекта — создать отзывчивый и надёжный инструмент для работы с файлами, радиосигналами и беспроводными интерфейсами на собственном оборудовании и в разрешённых средах.

Проект развивается постепенно: каждый аппаратный модуль должен проходить полный путь от команды интерфейса до получения, просмотра, сохранения и повторного использования данных.

> Для продолжения разработки в новом чате сначала полностью прочитайте
> [README_CODEX.md](README_CODEX.md). В нём находится актуальная контрольная
> точка, устройство памяти, архитектура Wi-Fi и план развития Embedded MAP.

## Аппаратная платформа

- ESP32-S3, 16 MB Flash;
- 8 MB Octal PSRAM, 80 MHz;
- дисплей ST7789, 320×170, RGB565;
- пять кнопок: UP, DOWN, LEFT, RIGHT и SELECT;
- внутренняя FAT-файловая система;
- целевая плата: Bruce / Smoochiee Board V2;
- планируемые интерфейсы: IR, Wi-Fi, NRF24 и CC1101.

## Что уже реализовано

- драйвер ST7789 с постоянным DMA ping-pong и canvas в PSRAM;
- кнопочное управление с распознаванием короткого и долгого SELECT;
- UI-движок со скруглённым курсором, popup и экранной клавиатурой;
- NVS и внутренний FAT-раздел;
- файловый менеджер: навигация, создание, чтение, запись, переименование и удаление;
- прокрутка списка и длинных имён;
- построчный редактор с кареткой, длинными строками и безопасным сохранением;
- отдельный FM worker для неблокирующих файловых операций;
- WiFi Worker: lifecycle, подключение, credentials, auto-connect и snapshots;
- список AP с числовым RSSI и общей клавиатурой для паролей;
- Air Monitor, channel hopping, ограниченный capture store и PCAP export;
- TCP scanner и отдельный экран `Embedded MAP`.

Последнее состояние обязательно сверяется с текущим кодом и сборкой: наличие реализации не означает, что каждый этап уже проверен на реальной плате.

## Текущий приоритет: завершение Wi-Fi-модуля

FM и mini-IDE остаются фундаментом и не должны ломаться. Ближайшая работа:

1. Сохранить state/errno/latency для каждого проверенного TCP-порта.
2. Сделать scrollable результаты `Embedded MAP` вместо одних счётчиков.
3. Добавить manual IPv4 и ограниченный Custom port range.
4. Проверить connect/disconnect/auto-connect после холодных перезапусков.
5. Провести soak-тесты scanner/Air Monitor/PCAP на утечки памяти.
6. Добавить минимальное bounded service detection только для open ports.
7. Сохранять versioned scan report через FM worker.

Подробный порядок и memory budget описаны в разделах 19–22
[README_CODEX.md](README_CODEX.md).

## Дорожная карта

### 1. Инфракрасный модуль

- законченный UI и недостающие экраны;
- несколько распространённых IR-протоколов;
- захват сырых импульсов через RMT;
- анализ, сохранение, загрузка и повторное воспроизведение сигналов;
- чёткое разделение декодированных команд и raw-сигналов;
- проверка таймингов, ограничений памяти и безопасного владения RMT-буферами.

### 2. Развитие UI-движка

UI будет рефакториться по мере появления реальных вертикальных сценариев. Изменения должны улучшать повторное использование экранов, модальных элементов и интерактивных объектов, не ломая уже проверенное управление.

### 3. Беспроводные и радиомодули

После IR функции добавляются постепенно, по одному законченному вертикальному срезу:

- Wi-Fi;
- NRF24;
- CC1101.

Для каждого модуля целевой поток одинаков: **UI-команда → аппаратная worker-задача → результат → просмотр → сохранение → загрузка → повторное использование**. Долгие аппаратные операции не должны блокировать UI.

Ранний дизайн WiFi Worker находится в
[docs/WIFI_WORKER_DESIGN.md](docs/WIFI_WORKER_DESIGN.md), но фактическое
состояние и текущие API зафиксированы в [README_CODEX.md](README_CODEX.md).

### 4. Определение протоколов

После накопления рабочих захватов и устойчивых декодеров планируется компактный классификатор примерно на **100–200 нейронов** для предварительного определения протокола или типа сигнала. Его архитектура и признаки будут выбраны только на основе реальных данных и измерений на ESP32-S3. Детерминированные проверки и обычные декодеры останутся основным надёжным путём; модель будет помощником, а не единственным источником решения.

## Архитектурные принципы

- UI не выполняет долгие файловые, сетевые или аппаратные операции.
- Worker-задачи не рисуют интерфейс.
- Render читает состояние, но не изменяет файловую или аппаратную модель.
- Одна команда должна иметь один однозначный итоговый ответ.
- Новые возможности добавляются небольшими проверяемыми этапами.
- Сборка ESP-IDF, host-тест и проверка на ESP32-S3 считаются разными уровнями проверки.
- Проверяются коды ошибок, границы строк, владение состоянием и время жизни DMA/RMT-буферов.
- Рабочее проверенное управление не меняется без конкретной причины.

## Известный технический долг

- Embedded MAP пока хранит подробный список только открытых портов;
- `F/E` необходимо объяснять точным `errno` и latency каждой probe;
- capture store ограничен 512 пакетами и требует длительных overflow-тестов;
- connect/auto-connect и освобождение promiscuous mode требуют soak-тестов;
- FM/редактор остаются под регрессионным контролем при изменениях Wi-Fi.

Эти направления не объединяются в один широкий рефакторинг.

## Сборка и прошивка

Требуется установленное окружение ESP-IDF. Проект ранее собирался на development-версии ESP-IDF 6.1, поэтому перед изменением API необходимо проверять фактический `IDF_VER` локального SDK.

```bash
idf.py build
idf.py -p PORT flash monitor
```

Стабильный проектный вход не требует ручного `export.ps1` и работает при
запрещённом прямом запуске PowerShell-скриптов:

```bat
scripts\flash_jtag_fresh.cmd -BuildOnly
scripts\flash_jtag_fresh.cmd
```

Первая команда только собирает и проверяет свежесть артефакта. Вторая выполняет
build, JTAG flash, verify и reset. Скрипт отказывается прошивать `IoTSE.bin`,
если binary старее исходников.

Очистка конфигурации и сборки:

```bash
idf.py fullclean
```

Существующий `sdkconfig` имеет приоритет над `sdkconfig.defaults`.

## Разделы Flash

- NVS: `0x9000`, 24 KB;
- PHY init: `0xF000`, 4 KB;
- factory application: `0x10000`, 4 MB;
- internal FAT storage: оставшиеся 10 MB.
