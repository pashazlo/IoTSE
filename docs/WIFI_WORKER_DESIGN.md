# WiFi Worker: архитектура и этапы реализации

Статус: lifecycle и backend сканирования реализованы; UI ещё не подключён и
проверка радио на ESP32-S3 не выполнена.

## Цель

WiFi Worker — единственный владелец состояния Wi-Fi-драйвера ESP-IDF. UI только
отправляет короткие команды и получает результаты без ожидания радиоопераций.
Первый законченный сценарий: запустить разрешённое сканирование, показать список
сетей, сохранить снимок и затем снова открыть его через файловый менеджер.

## Границы ответственности

- UI владеет фокусом, выбранной строкой и отображаемой копией результата.
- WiFi Worker владеет `esp_wifi_*`, режимом радио и текущей операцией.
- callback ESP-IDF только переносит маленькое событие в очередь worker; он не
  рисует UI, не пишет файлы и не выполняет тяжёлый разбор.
- FM Worker остаётся единственным владельцем файловых операций. WiFi Worker не
  вызывает `fopen`, `rename` или другие функции файловой системы.
- Сохранение снимка будет отдельной передачей неизменяемых данных WiFi → FM, а
  не прямой записью файла из WiFi callback.

## Состояния

```text
OFF -> STARTING -> IDLE -> SCANNING -> IDLE
 ^                    |
 +------ STOPPING <---+

Любая ошибка запуска переводит worker в ERROR. Команда STOP должна пытаться
освободить радио и вернуть состояние OFF даже после частичной инициализации.
```

Переходы выполняет только задача worker. Состояние не меняется напрямую из UI
или системного Wi-Fi callback.

## Публичные команды

Каждая принятая команда получает `request_id`. На неё публикуется ровно один
терминальный ответ с тем же `request_id`.

```c
typedef enum {
    WIFI_WORKER_CMD_START = 0,
    WIFI_WORKER_CMD_SCAN,
    WIFI_WORKER_CMD_STOP,
} wifi_worker_cmd_type_t;
```

- `START` — лениво инициализировать netif/event loop/STA и запустить радио.
- `SCAN` — начать одно сканирование с явными параметрами.
- `STOP` — остановить радио и освободить только те ресурсы, которыми владеет
  worker.

Отмена сканирования пока не входит в публичный контракт: при одной pending-
команде новый запрос не принимается до `SCAN_DONE`. Её следует добавить вместе
с отдельным внутренним каналом управления, чтобы и исходный `SCAN`, и команда
отмены получали однозначный результат без потери события в mailbox.

Параметры `SCAN` первого этапа:

```c
typedef struct {
    uint8_t channel;       // 0 — все поддерживаемые каналы
    bool show_hidden;
    bool passive;
    uint16_t dwell_ms;     // проверяется и ограничивается worker
} wifi_scan_request_t;
```

Worker обязан проверять enum, канал и время пребывания до вызова ESP-IDF. Строки
и указатели из UI в команду не передаются: очередь хранит самодостаточную копию.

## Ответы

Промежуточные события ESP-IDF остаются внутренними. В UI идут только
терминальные ответы:

```c
typedef enum {
    WIFI_WORKER_RESULT_STARTED = 0,
    WIFI_WORKER_RESULT_SCAN_READY,
    WIFI_WORKER_RESULT_CANCELLED,
    WIFI_WORKER_RESULT_STOPPED,
    WIFI_WORKER_RESULT_ERROR,
} wifi_worker_result_type_t;

typedef struct {
    wifi_worker_result_type_t type;
    wifi_worker_cmd_type_t command;
    uint32_t request_id;
    uint32_t snapshot_generation;
    esp_err_t error;
} wifi_worker_result_t;
```

`ESP_OK` при отправке команды означает только, что команда скопирована в
очередь. Фактический итог находится в `wifi_worker_result_t`.

## Снимок сетей

Первый лимит — 64 точки доступа. Он ограничивает память и время сортировки, но
не заявляется как количество всех сетей в эфире.

```c
#define WIFI_SNAPSHOT_MAX_APS 64

typedef struct {
    char ssid[33];
    uint8_t bssid[6];
    int8_t rssi;
    uint8_t primary_channel;
    uint8_t secondary_channel;
    uint8_t auth_mode;
} wifi_ap_record_t;

typedef struct {
    uint32_t generation;
    uint16_t count;
    bool truncated;
    wifi_ap_record_t records[WIFI_SNAPSHOT_MAX_APS];
} wifi_scan_snapshot_t;
```

Worker собирает staging-снимок, сортирует его по RSSI, затем публикует целиком.
Контроллер копирует готовый snapshot в своё состояние короткой операцией; render
не держит mutex и не читает память, которую worker может менять. Поле
`truncated` явно показывает, что драйвер видел больше записей, чем помещается.

SSID всегда копируется ограниченно и завершается `\0`. BSSID хранится бинарно,
а форматируется только в UI/экспорте. Пустой или невалидный SSID не используется
как идентификатор: стабильная идентичность записи — BSSID + канал.

## Очереди и конкурентность

- внешняя очередь команд имеет глубину 1;
- UI допускает только одну pending-команду Wi-Fi;
- очередь терминальных результатов — mailbox глубиной 1;
- отдельная внутренняя очередь переносит события ESP-IDF в задачу worker;
- callback использует неблокирующую отправку и не выделяет память;
- большие списки и пакеты никогда не копируются через FreeRTOS queue;
- повторный `SCAN` во время `SCANNING` отклоняется, а не запускает вторую
  операцию поверх первой.

Для внутренней очереди нельзя молча терять критический `SCAN_DONE`. Если она
заполнена, callback выставляет атомарный overflow-флаг, worker завершает запрос
ошибкой и возвращает радио в известное состояние.

## Память и данные пакетов

Сканирование сетей и захват кадров — разные подсистемы одного worker. Сначала
реализуется только сканирование. Будущий callback приёма пакетов будет копировать
ограниченный заголовок/кадр в заранее выделенный ring buffer. Никаких `malloc`,
логирования payload или разбора протокола внутри callback.

Для захвата заранее задаются:

- максимальная длина сохраняемого кадра;
- число слотов ring buffer;
- счётчики `received`, `stored`, `dropped`, `truncated`;
- монотонная временная метка;
- канал и RSSI;
- фильтр типов кадров.

Переполнение должно увеличивать `dropped`, а не повреждать память и не блокировать
Wi-Fi task ESP-IDF. Полезная нагрузка, ключи и учётные данные не выводятся в лог.

## Вертикальные этапы

1. **Контракт и сборочная контрольная точка** — этот документ, восстановление
   корректного ESP-IDF окружения, сборка без изменения runtime.
2. **Lifecycle worker** — реализовано: очереди, задача, `START/STOP`, повторная
   инициализация и очистка после частичного старта; UI ещё не меняется.
3. **Scan backend** — реализовано без cancel/timeout: одна команда `SCAN`,
   асинхронный `SCAN_DONE`, snapshot и проверка границ. Требуется тест на плате.
4. **Scan UI** — Wi-Fi → Scan, pending/error, список SSID/RSSI/channel/security,
   прокрутка и возврат без блокировки UI.
5. **Подключение к собственной AP** — экран credentials, единая клавиатура с
   верхним/нижним регистром, команда connect/disconnect и состояние IP/маски/
   gateway. Пароль не возвращается в событиях, не пишется в лог и хранится в
   NVS только после отдельного решения пользователя.
6. **Сохранение** — стабильный версионированный формат снимка, передача FM
   Worker, безопасная запись и повторное открытие.
7. **Пассивный лабораторный анализ** — ограниченный ring buffer, статистика
   потерь, фильтрация и просмотр метаданных на собственном стенде.

Каждый этап завершается отдельной сборкой и проверкой на ESP32-S3. Активные
радиофункции, инъекция и сценарии вмешательства не смешиваются с фундаментом
сканера и требуют отдельного дизайна, ограничений и проверки разрешённой среды.

## Проверки перед первым runtime-коммитом

- точная версия ESP-IDF и локальные сигнатуры `esp_wifi_*`;
- повторный `START`, `STOP` из каждого промежуточного состояния;
- отказ выделения очереди/задачи/буфера;
- заполненная command queue и повторное нажатие SELECT;
- timeout и отмена scan;
- 0, 1, 64 и более 64 результатов;
- скрытый SSID, максимальный SSID, дубликаты SSID с разными BSSID;
- high-water mark задачи и свободная internal/PSRAM до и после сканирования;
- отзывчивость кнопок и UI во время полного сканирования.
